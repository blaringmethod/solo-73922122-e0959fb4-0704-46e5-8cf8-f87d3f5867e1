# 积水格入仓（巡查包 → SQLite → 框查/单格查询/历史工区复核）

一个 Flask + SQLite 的小服务：导入巡查包 JSON，把「覆盖范围」和「现行积水格」一起落库，
并提供框查、单格查询与**历史包工区积水复核**网页。覆盖范围按矩形存储，不逐格展开；
框查只读现行状态，不回放历史积水点，历史复核则按包回放归档信息。

## 快速启动

```bash
docker compose up --build
```

打开 <http://localhost:8000> 。数据落在命名卷 `flood-data` 的 `/data/flood.sqlite3`。
Compose 里设置了 `FLOOD_ALLOW_RESET=1`，网页上的「清空演示库」按钮才会生效。

本地（不用 Docker）：

```bash
python3 -m pip install -r requirements-dev.txt
FLOOD_ALLOW_RESET=1 python3 -m gunicorn --bind 127.0.0.1:8000 --workers 2 --threads 4 wsgi:app
# 或 python3 wsgi.py
```

## 包格式

```json
{
  "version": 7,
  "coverage": {"row_start": 0, "row_end": 50, "col_start": 0, "col_end": 20},
  "wet_cells": [[12, 4], [12, 5], [31, 2]]
}
```

- `version` 必须是正整数；`coverage` 四个字段都是整数，区间**左闭右开**（`row_end`/`col_end` 不含）。
- `wet_cells` 是 `[row, col]` 整数对，必须落在覆盖矩形内；重复坐标会被合并。
- 覆盖矩形内**未列出**的格子 = 已巡查、无积水。矩形外 = 未巡查。
- 未知字段会被拒绝（防止把拼错的 `wet_cells` 误读成「整片无积水」）。
- 上限：坐标 / 版号绝对值 ≤ 2,000,000,000（R*Tree 的 32 位范围），列出的积水点 ≤ 500,000 个。
  覆盖面积**不设上限**，也不展开。

## 语义

| 规则 | 实现 |
| --- | --- |
| 交叠处看最高版号 | 新包覆盖矩形内，旧版号（≤ 本包版号）的现行积水格先被清除，再写入本包列出的格；若某些格已被**更高**版号覆盖，它们的判定保留，不被旧包覆盖。 |
| 旧包晚到也能补新版没查过的地方 | 旧包只影响自己矩形内、且没有更高版号覆盖的区域；矩形外/新版已覆盖处不动。 |
| 没报积水点 = 可能已退水 | 包内 `wet_cells` 为空时正常入库，覆盖范围记为「已巡查无积水」，已清除该范围内的旧积水。响应里带 `warning` 提示这不是错误。 |
| 同版同内容重传不改变结果 | 对规范化后的内容（坐标排序去重、固定键序）取 SHA-256。摘要相同返回 `200 unchanged`，不写库。 |
| 同版异内容整包退回 | 摘要不同返回 `409 version_conflict`，整个事务回滚。 |
| 入库失败继续提供原结果 | 每次导入是单个 `BEGIN IMMEDIATE` 事务（覆盖矩形、现行积水、原报归档同生共死）；任何异常（校验、冲突、SQLite 错误）都回滚，覆盖矩形、现行积水与归档保持原样，服务继续响应旧数据。 |
| 新包原报点全部保留 | 入仓即在同事务归档全部 `wet_cells`，即使入仓时已被高版覆盖，历史复核仍能查到确数。 |
| 旧包冻结升级时认知 | 升级迁移把旧包仍生效的湿格快照、被高版覆盖的矩形范围冻结；之后复测只改现行状态，不改冻结结果。 |

覆盖与现行积水的存储：

- `coverage_rects`：**每包一行矩形**。SQLite 支持 R*Tree 时建虚拟表（有 `rtree_i32` 索引），
  不支持的构建自动退化为带索引的普通表，列名一致、SQL 共用。
- `current_wet`：**只存现行**积水格 `(row, col) → 生效版号`，没有全量历史表。
  因此框查是 `current_wet` 上的一次范围扫描，历史包再多也不会变慢，也不会重扫旧积水点。
- `packages`：版号、摘要、覆盖矩形副本、原始列出点数、入库时间、`historical` 类型标记。
- `package_wet_archive`：每包**原报积水点**归档。新包入仓时在同一事务写入全部原报点，
  即使入仓时已被更高版覆盖也保留；升级前已在仓的旧包只快照升级时仍能确定的湿格。
- `package_unknown_rects`：仅旧包使用，冻结升级时刻被更高版覆盖的矩形（已裁剪到旧包覆盖内），
  按矩形存、按矩形并集查询，**不逐格展开**；之后的复测永不修改这些行。

单格状态：`wet`（有积水，带生效版号）/ `dry`（已查无积水，带作出该判定的最高覆盖版号）/ `unsurveyed`（未巡查）。
注意：`dry` 的版号取「覆盖该格的最高版号」，这是产生当前结论的那一代巡查。

## 历史工区积水复核

养护人员复核灾情汇总时，需要回答：**某次巡查（某个已入仓版号）在指定工区矩形内报了多少积水格？**
工区只统计与该包覆盖矩形的**交集**（左闭右开，矩形运算，不逐格展开覆盖范围）。

### 新包（本次升级后入仓，`historical = 0`）

- 入仓时把包内全部原报积水点写入 `package_wet_archive`，与现行状态在**同一个事务**里生效；
  写入失败整体回滚，原有数据保留。
- 即使某个原报点入仓时已被更高版覆盖（现行表里不存在），归档里仍在，复核得到**确数**。
- 交集内答案恒为 `min_wet = max_wet`，接口直接返回 `count`。

### 旧包（升级前已在仓，`historical = 1`）

升级（schema v1 → v2）在一个事务里冻结旧包当时的认知，之后任何复测都不再改变它：

| 格子类型 | 判定来源 |
| --- | --- |
| 已知湿 | 升级时仍生效、且归属该包的现行湿格，快照进 `package_wet_archive` |
| 未知 | 升级时被更高版覆盖矩形盖住的格子，并集存于 `package_unknown_rects`（矩形，不展开） |
| 已知干 | 交集内其余格子：在覆盖范围内、非未知、非已知湿 |

设交集内已知湿 `W`、未知格数 `U`，该包**原报积水总数** `T`（`packages.wet_count`，整包口径），
交集外未知格 `Uout`、交集外已归档湿 `Wout`、未归档的原报点数 `R = T − 归档总数`：

- 最少：`W + max(0, R − Uout)` —— 交集外未知格装不下的原报点，必须落在工区未知格里；
- 最多：`W + min(U, T − Wout)` —— 工区未知格全部湿，也不能超过剩余原报点。
- 两值相同即报确数（`exact: true`，给 `count`）；不同返回区间 `min_wet – max_wet`。
- 后来更高版复测覆盖旧包时，只改动 `current_wet` / `coverage_rects`，
  **不触碰**归档与未知矩形，升级时能确定的干湿与未知范围保持不变。

未知矩形的并集面积用扫描线 + 列区间合并计算（O(n² log n)，n = 相交矩形数），
覆盖百万格也只处理矩形，不生成逐格数据。

## 网页

1. **导入巡查包**：粘贴 JSON 或选择 `.json` 文件；六个示例按钮覆盖首次巡查 / 覆盖旧结果 /
   旧包晚到 / 同内容重传 / 同版异内容 / 清空。
2. **已入仓巡查包**：每个包的覆盖矩形、包内点数、现行点数、归档点数与新包/旧包标记、摘要、时间。
3. **框查现行积水格**：行列半开区间 + 返回上限；SVG 里覆盖矩形按矩形画（不逐格），
   红点为现行积水；表格列出结果，截断时提示。
4. **历史包工区积水复核**：下拉选已入仓版号 + 填工区矩形。新包直接给确数；
   旧包给最少/最多（相等即确数），SVG 区分已知湿（红）、已知干（绿）、未知（黄虚线），
   并列出原报总数与交集外约束，便于人工核对推导。
5. **单格查询**：显示三种状态之一。

## API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/packages` | 导入；同事务写入覆盖、现行状态与原报点归档。`201 imported` / `200 unchanged` / `400 invalid_package` / `409 version_conflict` |
| `GET` | `/api/packages` | 包列表（含 `historical`、`archived_wet_points`）、最高版号、现行积水总数 |
| `GET` | `/api/wet?row_start=&row_end=&col_start=&col_end=&limit=` | 框内现行积水格 + 相交的覆盖矩形；`limit` 默认 2000、最大 5000，超出置 `truncated: true` |
| `GET` | `/api/history/wet?version=&row_start=&row_end=&col_start=&col_end=&limit=` | 历史工区复核：交集、已知湿/干、未知格、`min_wet`/`max_wet`、`exact`/`count`、未知矩形与归档点；版号不存在返回 `404 package_not_found` |
| `GET` | `/api/cell?row=&col=` | 单格 `wet` / `dry` / `unsurveyed` |
| `GET` | `/healthz` | 健康检查 |
| `POST` | `/api/reset` | 仅 `FLOOD_ALLOW_RESET=1` 时可用（演示用），同时清空归档与未知矩形 |

错误响应统一 `{"error", "message", "details", "committed": false}`。

## 已知未完成 / 取舍

- **并发写入是库级串行**：用 `BEGIN IMMEDIATE` + `busy_timeout` 保证一致性，导入会排队。
  已验证 16 并发 × 10 个包全部 `201`、无 `database is locked`，但吞吐不是目标。
- **`dry` 不存逐格状态**：靠「覆盖矩形 + 现行积水」推导。这是「覆盖范围不得逐格展开」的直接后果；
  代价是单格 `dry` 查询要查覆盖矩形索引（R*Tree/普通索引），而不是 O(1) 点查。
- **旧包的未知格无法还原逐格干湿**：升级时被高版覆盖的格子只冻结了矩形范围，
  原报点落在其中的具体位置已不可考，因此只能给最少/最多区间；这是需求规定的信息边界。
- **框查上限 5000**：大范围框查会截断（明确返回 `truncated`），未做分页/流式导出。
  历史复核的归档点展示同样限 5000（计数走 SQL `COUNT(*)`，不受截断影响）。
- **没有鉴权、没有多用户/审计日志**；`/api/reset` 仅为演示。
- **没有前端自动化测试框架**：用 jsdom 做了冒烟（页面渲染、历史复核三种结果、无 JS 报错），
  但未纳入 CI。
- **Docker 只在无 Docker 守护进程的环境验证过配置**（YAML/Dockerfile/依赖），
  实际 `docker compose up` 需在有 Docker 的机器上跑；本地用同一 gunicorn 命令等价验证。
- 版号不连续/跳跃是允许的（包是独立巡查批次），未做「版号必须 +1」的约束。
- 同一版号重传时只比较规范化内容，不比较 JSON 的原始字节（这是刻意的：键序/空白不同仍算同内容）。
